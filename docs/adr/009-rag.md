# ADR-009 — Version-aware knowledge architecture

- Status: Proposed
- Date: 2026-09-21

## Context

Documentation guides test selection but is untrusted, can contain prompt
injection and may describe a different product version. Retrieval quality must
not undermine the separation between claims and runtime evidence.

## Decision

Persist immutable source documents and deterministic chunks with product,
version/range, source, section, dates, digest, parser version and trust labels.
Apply product/version filters before ranking. Cross-version fallback is explicit
and labelled. Retrieval produces attributed `DocumentationClaim` records, never
runtime evidence.

Start with SQLite FTS5 and metadata filters. Add embeddings and a local vector
adapter only after retrieval evals demonstrate a material semantic-recall gap.

## Alternatives considered

- A distributed vector database supports scale but adds a service before corpus
  size or retrieval benchmarks justify it.
- Embeddings-only retrieval handles paraphrase but can obscure exact version and
  term matching.
- Feeding whole repositories to an LLM increases cost and injection exposure.
- Treating current web docs as timeless loses reproducibility.

## Consequences

The initial pipeline is transparent, local and version-correct. Semantic recall
may be lower until hybrid retrieval is justified. Source citations and raw text
allow claims to be challenged.

## Risks

Missing or incorrect version metadata can still contaminate retrieval. Unknown
versions fail visibly, source provenance is retained, and cross-version tests are
release gates.
